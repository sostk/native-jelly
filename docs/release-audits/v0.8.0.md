# Release audit — v0.8.0

The evidence behind [the v0.8.0 release note](https://github.com/sostk/native-jelly/blob/main/docs/release-notes/v0.8.0.md). Written for a webosbrew reviewer, a contributor auditing an old release, and us in a year. The section at the bottom is generated from the artifact that was published; everything above it was written by a person before the release ran.

v0.8.0 is the first release of Native Jelly (`com.sostk.nativejelly`). It is cut from `main` after PlxNative v0.7.0 (`com.beb.plxnative`, [audit](https://github.com/sostk/native-jelly/blob/main/docs/release-audits/v0.7.0.md)), and between the two the app was rebuilt as a Jellyfin client: the Plex sign-in screens were removed, and sign-in, browsing, playback and progress reporting now speak Jellyfin's API (`rust-modules/src/jf/`, [docs/jellyfin-playback.md](https://github.com/sostk/native-jelly/blob/main/docs/jellyfin-playback.md), [docs/multi-user.md](https://github.com/sostk/native-jelly/blob/main/docs/multi-user.md)). Nothing in v0.7.0's device evidence below carries over: it graded a different app against a Plex server.

## External compatibility reports known at release time

None for Native Jelly. The third-party reports in v0.7.0's audit (a 2019 k5lp set on v0.6.3, an LG 65UP7560AUD on v0.2.1) were made against PlxNative playing from Plex servers. They are not carried over: the player pipeline is shared, but the server, the negotiation and the delivery are not, and one report is never generalised to a neighbouring release, let alone a different app.

- **Plays video, reported:** empty. v0.7.0's two reports belong to PlxNative and are not carried over (see above).

## Known issues at release, with provenance

- **https through a reverse proxy.** On the maintainer's own server, playback reached over https through a reverse proxy failed where the same server over http on the LAN played (reported in development, October 2026). Two causes were identified and are not fixed in this release: the proxy closing long-lived media reads, and the HTTP reader refusing a full `200` answer to a ranged request (`net/curlio`). Not measured on any other proxy.
- **End of a progressive transcode.** Against a loopback stand-in for a Jellyfin server, a transcode that reached its end read as a transport failure rather than an end of stream. Not yet seen against a real server; not in the note until it is.
- **Re-encode is always H.264** even on a server allowed to encode HEVC: the setting cannot be read, and a lane that guessed HEVC loaded the pipeline for a codec that never came ([docs/jellyfin-playback.md](https://github.com/sostk/native-jelly/blob/main/docs/jellyfin-playback.md), Limitations).
- **Live TV** (`RequiresOpening`, `LiveStreamId`) is not modelled.
- **HLS** is asked for only mid-play under Auto and its rung candidates; the player's segment loop on Jellyfin playlists is covered by loopback tests only, not by the simulator or a set. Auto plays the original on a server signed in at a private or `.local` address (`catalog/probe.rs` `configured_tier`), so this path is reached only off the LAN. A static review of `main` before this release (2026-10-18) found two likely defects there, neither reproduced: the HLS profile offers AC-3/E-AC-3/DTS audio while the segment demuxer accepts only AAC (`hls: demux failed: HLS segment audio is not AAC`), and a master playlist with Jellyfin's trickplay `#EXT-X-IMAGE-STREAM-INF` tag is refused as an unknown tag. The note asks for reports instead of claiming either way.
- **No codec table on webOS 6.5.3.** On the C1 above, `/etc/umediaserver/device_codec_capability_config.json` does not exist, so the app falls back to the 49SM9000PLA's capabilities (`devcaps: … unreadable … assuming the 49SM9000PLA profile`, `jf: capabilities … table=assumed`). That profile played on this set; what the C1's decoders could take beyond it is not offered to the server.

## Deliberately not done

- **No migration from PlxNative.** The app id changed (`com.beb.plxnative` → `com.sostk.nativejelly`), so this app cannot read PlxNative's storage, and a Plex sign-in would be useless to it anyway. The note says so in its first section.
- **Records written by pre-release Native Jelly builds.** The rebrand renamed two on-disk format markers; builds of this app id from 5 to 7 October 2026 wrote the old names. Both are read under either name and written under the new one (#12). The keymanager key name was renamed in the same change (`plxnative.session.v1` → `nativejelly.session.v1`), so on sets that seal the session with keymanager, a session sealed during that window names a key this build does not request. Only development builds wrote it, none was released, and the cost is one sign-in; opening it needs a firmware-compatibility review and a device, so it was not done.
- **`SelectProfileWithReply` / `AppMsg::SelectionReply`** have no production sender or consumer since the Plex profile picker was removed; they are kept, under test (#13), and not used.
- **No webosbrew listing update in this change.** `docs/webosbrew-package.yml` and the `webosbrew/apps-repo` submission for `com.sostk.nativejelly` are separate artifacts and follow this release.

## Release configuration

| | |
|---|---|
| flavour | `com.sostk.nativejelly` (stable) — the id users install; `FLAVOR: stable` is pinned in the release workflow's build job |
| cargo features | `RELEASE=1`, which drops `devtools` and `devtriggers` |
| built by | GitHub Actions, from the tag, at a path identical on every runner |
| toolchain | webOS NDK unchanged since v0.7.0; Rust nightly pinned by date in the `RUST_NIGHTLY` repository variable |

What is unusual about this build, relative to v0.7.0:

- **A new app id and a new binary name.** `com.beb.plxnative` → `com.sostk.nativejelly`; the executable is `nativejelly` and the storage helper `nativejelly-storage`. Every runtime path, log name and the private DB8 kind follow the id.
- **Different network hosts.** The app is meant to talk to the Jellyfin server address the person types, plus the crash-report and analytics endpoints only for someone who opts in. The catalog layer still carries PlxNative's plex.tv request code (`rust-modules/src/catalog/`), so the generated host-string table below will still show plex.tv; with no Plex sign-in left, no path to it is expected, but none was traced for this audit. The table is the measurement; this paragraph is the expectation.
- **Credentials over plain http, with consent.** A release build still refuses to send a credential over http on its own (`CredentialPolicy::HttpsOnly`). A Jellyfin server that answers only over http can be allowed once, per server id at that exact address, after the anonymous `/System/Info/Public` at that address names that server; the answer is kept with the Jellyfin record and listed under Settings → Unencrypted connections. The note carries this as an action-required section because a password then crosses the network unencrypted.
- **Telemetry goes to this project's own projects.** Optional crash reports (Sentry) and analytics (PostHog), both off until the person opts in, use the endpoints in the `NJ_SENTRY_DSN` and `NJ_POSTHOG_KEY` repository variables; the build fails closed if either is unset. Debug symbols upload to the `SENTRY_ORG` / `SENTRY_PROJECT` repository variables (both `native-jelly`); with `SENTRY_PROJECT` unset the workflow falls back to `native-jelly` (#15).
- **The Rust tree was split into crates** (`nj_base`, `nj_machine`, `nj_platform`, `nj_gfx`, `nj_net`, storage). The generated `DT_NEEDED` list and firmware matrix are the evidence that this changed nothing at load time.
